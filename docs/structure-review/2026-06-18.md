# Code Structure Review - 2026-06-18

## Scope

- Reviewed all route modules under `src/routes/**`, including page/layout server files, endpoint files, and Svelte page/layout components.
- Reviewed `src/lib/**` exports, schemas, server logic, hooks, utilities, and app/shared components.
- Excluded `src/lib/components/ui/**` from findings as requested.
- Focus areas:
  - import placement and server/client boundaries
  - duplication across routes and shared modules
  - SvelteKit lifecycle usage
  - error handling consistency
  - dead code / unused exports / ghost patterns
  - TypeScript strictness and generated `$types` usage

## Executive Summary

The codebase is broadly well organized: schemas are centralized, route files consistently use generated `./$types` in most places, and no server-only `$lib/server/*` imports were found in reviewed `.svelte` components. I also did not find broad `onMount` misuse across the reviewed route/component surface.

The main structural risks are concentrated in a few areas:

- reminder email delivery errors are swallowed and can still be logged as successful sends
- `src/routes/(app)/visits/[id]/+page.server.ts` flattens meaningful `400/404` failures into generic `500` responses
- several route and dialog modules repeat the same ownership / form / redirect patterns instead of sharing stronger abstractions
- a few large route modules (`src/routes/(app)/tasks/+page.server.ts` at 997 lines and `src/routes/(app)/dashboard/+page.server.ts` at 775 lines) are accumulating too many responsibilities

## Findings

### DRY & Abstraction

#### Finding 1

- **Severity:** Medium
- **Affected file(s):**
  - `src/routes/(app)/tasks/+page.server.ts`
  - `src/routes/(app)/dashboard/+page.server.ts`
- **Issue description:** These route modules have grown into large orchestration files that mix query construction, data shaping, validation helpers, action handling, and route-level response assembly. The tasks page server is 997 lines and the dashboard page server is 775 lines.
- **Why it matters:** Large route files become the place where every new concern lands, which makes reuse harder, testing more brittle, and changes riskier because unrelated logic lives side-by-side.
- **Recommended fix:** Split each file into feature-focused server modules. For example: dashboard query loaders + mappers in `$lib/server/dashboard/*`, and task board / mood / agenda action helpers in `$lib/server/tasks/*`, leaving `+page.server.ts` as a thin composition layer.

#### Finding 2

- **Severity:** Medium
- **Affected file(s):**
  - `src/routes/(app)/fitness/meals/[id]/edit/+page.server.ts`
  - `src/routes/(app)/fitness/weight/[id]/edit/+page.server.ts`
  - `src/routes/(app)/fitness/workouts/[id]/edit/+page.server.ts`
  - `src/routes/(app)/tasks/[id]/edit/+page.server.ts`
  - `src/lib/server/actions/edit-route-helpers.ts`
- **Issue description:** The edit routes all follow the same structure: load owned entity, validate form, re-check ownership, mutate, log, and redirect. `edit-route-helpers.ts` only abstracts the lookup step, so most update/delete ceremony is still repeated file-by-file.
- **Why it matters:** Authorization checks, status handling, and redirect behavior can drift between routes even though they represent the same edit-route pattern.
- **Recommended fix:** Extend the shared helper layer to cover common edit/delete flows, or introduce per-domain service functions so route files only wire request parsing to shared mutations.

#### Finding 3

- **Severity:** Medium
- **Affected file(s):**
  - `src/lib/components/fitness/dialogs/LogWeightDialog.svelte`
  - `src/lib/components/fitness/dialogs/LogMealDialog.svelte`
  - `src/lib/components/fitness/dialogs/LogWorkoutDialog.svelte`
  - `src/lib/components/fitness/dialogs/CreateReminderDialog.svelte`
  - `src/lib/components/fitness/dialogs/SetGoalWeightDialog.svelte`
  - `src/lib/components/fitness/dialogs/SetCalorieTargetDialog.svelte`
- **Issue description:** These dialogs repeat the same open-state plumbing, `superForm` success/error toast handling, trigger button styling, cancel/footer layout, and edit-vs-create branching. The shared green CTA class string (`bg-green-600 text-white hover:bg-green-700`) is duplicated across the same family of files.
- **Why it matters:** Any UX or behavior fix must be repeated in several places, which increases maintenance cost and makes inconsistencies more likely.
- **Recommended fix:** Extract a small shared dialog shell or controller pattern for form dialogs, plus a shared CTA variant/component for the repeated submit/trigger styling.

#### Finding 4

- **Severity:** Low
- **Affected file(s):**
  - `src/routes/(auth)/sign-in/+page.server.ts`
  - `src/routes/(auth)/register/+page.server.ts`

### Error Handling

#### Finding 1

- **Severity:** High
- **Affected file(s):**
  - `src/lib/server/email/index.ts`
  - `src/lib/server/email/email-notifications.ts`
- **Issue description:** Multiple email helpers in `src/lib/server/email/index.ts` catch send failures and `return error` instead of throwing. `processWorkoutReminders()` in `email-notifications.ts` awaits `sendWorkoutReminderEmail(...)`, then immediately sends a companion notification and logs the reminder as delivered. Because the email helper resolves with an error object instead of rejecting, failed sends can still be recorded as successful.
- **Why it matters:** Production reminder failures can be silently misclassified as successes, which breaks retry logic, obscures delivery problems, and weakens operational trust in the notification system.
- **Recommended fix:** Make send helpers either throw on failure or return an explicit discriminated result type. Update reminder processors to branch on success before logging `email_notifications`.

#### Finding 2

- **Severity:** High
- **Affected file(s):**
  - `src/routes/(app)/visits/[id]/+page.server.ts`
- **Issue description:** Several actions (`logVisit`, `updateVisit`, `updatePerson`, `archivePerson`, `deletePerson`, `deleteVisit`) throw `error(400/404, ...)` inside `try` blocks and then catch all errors, converting them into generic form messages or `500` errors.
- **Why it matters:** Real ownership/not-found/validation failures lose their intended semantics. Users and callers get a generic server error even when the route already knows the correct `400` or `404`.
- **Recommended fix:** Re-throw `HttpError` and redirects, and only translate unexpected exceptions. Use the same pattern consistently across all actions in the file.

#### Finding 3

- **Severity:** Medium
- **Affected file(s):**
  - `src/routes/(app)/journal/+page.server.ts`
  - `src/routes/(app)/meditation/+page.server.ts`
  - `src/routes/(app)/visits/+page.server.ts`
- **Issue description:** These `load` functions catch all exceptions, log them, and return normal empty-state payloads such as `{ entries: [] }`, `{ routines: [], schedules: [], sessions: [] }`, or `{ people: [] }`.
- **Why it matters:** A true data access failure becomes visually indistinguishable from a legitimate empty state, which makes production issues harder to detect and can mislead users into thinking their data is gone.
- **Recommended fix:** Throw `error(500, ...)` for unexpected failures, or return an explicit degraded-state flag so the UI can distinguish “no data” from “load failed.”

### Dead Code & Exports

#### Finding 1

- **Severity:** Medium
- **Affected file(s):**
  - `src/lib/server/db/schema.ts`
- **Issue description:** Several exported Drizzle relation objects appear to be defined but not referenced anywhere else in `src/**`. Examples confirmed by search include `sessionRelations`, `accountRelations`, `emailNotificationsRelations`, `journalEntriesRelations`, `moodLogsRelations`, `tasksRelations`, and `visitStatusSettingsRelations`.
- **Why it matters:** Unused exports enlarge the apparent public surface area of the schema module and make it harder to tell which relations are actually part of the runtime query model.
- **Recommended fix:** Remove unused relation exports, or document/colocate them behind the concrete modules that require them if they are being preserved intentionally for future relational queries.

#### Finding 2

- **Severity:** Low
- **Affected file(s):**
  - `src/lib/server/email/index.ts`
  - `src/lib/server/email/email-notifications.ts`
- **Issue description:** `getNotificationTag()` in `src/lib/server/email/index.ts` only forwards to `getWorkoutNotificationTag()` and is only consumed in one place.
- **Why it matters:** This extra export does not add a meaningful abstraction and creates unnecessary indirection.
- **Recommended fix:** Import `getWorkoutNotificationTag()` directly where needed and remove the wrapper.

#### Finding 3

- **Severity:** Low
- **Affected file(s):**
  - `src/lib/components/fitness/dialogs/LogWorkoutDialog.svelte`
- **Issue description:** The file still contains a commented-out reactive block (`// $effect(() => { ... })`) that no longer participates in behavior.
- **Why it matters:** Commented-out implementation code adds noise and makes it harder to understand the active data flow around exercise serialization.
- **Recommended fix:** Remove the dead commented block or replace it with a short note if the behavior is intentionally deferred.

### TypeScript Strictness

#### Finding 1

- **Severity:** Low
- **Affected file(s):**
  - `src/routes/api/auth/[...all]/+server.ts`
  - `src/routes/api/cron/email-notifications/+server.ts`
  - `src/routes/api/healthz/+server.ts`
- **Issue description:** These endpoint modules use generic `RequestEvent` / `RequestHandler` imports from `@sveltejs/kit` instead of the generated route-local `./$types`.
- **Why it matters:** Using `./$types` keeps endpoint contracts consistent with the rest of the codebase and preserves route-local typing as files evolve.
- **Recommended fix:** Switch endpoint signatures to the generated `./$types` exports.

#### Finding 2

- **Severity:** Low
- **Affected file(s):**
  - `src/routes/(app)/fitness/meals/[id]/edit/+page.server.ts`
  - `src/routes/(app)/fitness/weight/[id]/edit/+page.server.ts`
  - `src/routes/(app)/fitness/workouts/[id]/edit/+page.server.ts`
  - `src/routes/(app)/tasks/[id]/edit/+page.server.ts`
  - `src/routes/(app)/journal/[id]/+page.server.ts`
  - `src/routes/(app)/meditation/routines/[id]/+page.server.ts`
- **Issue description:** Several `[id]` routes cast `params.id as string` even though generated SvelteKit types already guarantee the param exists as a string for those routes.
- **Why it matters:** These casts add noise, weaken the value of generated typing, and normalize avoidable type assertions in route code.
- **Recommended fix:** Remove the unnecessary casts and rely on `./$types`.

#### Finding 3

- **Severity:** Low
- **Affected file(s):**
  - `src/lib/server/email/index.ts`
- **Issue description:** The email helpers currently have an implicit mixed return contract: success resolves normally, failure resolves with an error object.
- **Why it matters:** TypeScript is not forcing callers to handle failure explicitly, which is part of why the swallowed-send issue was able to slip through.
- **Recommended fix:** Give the helpers an explicit `Promise<void>` contract and throw on failure, or adopt a typed success/error result object that callers must inspect.

### SvelteKit Lifecycle

#### Finding 1

- **Severity:** Medium
- **Affected file(s):**
  - `src/routes/(app)/visits/+page.svelte`
- **Issue description:** `activeTab` is initialized from `page.url.searchParams` once via `getInitialTab()` and then maintained as local `$state`. The URL is updated with `replaceState()`, but the component does not resync tab state if the search params change through browser navigation or same-route URL changes.
- **Why it matters:** The UI can drift from the actual URL state, which breaks the expectation that tabs and query params stay in sync.
- **Recommended fix:** Derive tab state directly from `page.url.searchParams`, or add a reactive sync effect that updates `activeTab` when the URL changes.

#### Finding 2

- **Severity:** Medium
- **Affected file(s):**
  - `src/lib/utils/journal-context.ts`
- **Issue description:** This utility uses browser-only APIs (`navigator.geolocation` and `fetch`) but lives in a generic `$lib/utils` module without a browser-specific naming or placement boundary.
- **Why it matters:** The module is easy to import from SSR/server code later, which would create avoidable runtime boundary mistakes.
- **Recommended fix:** Move it to a browser-specific module name/location such as `journal-context.browser.ts`, or colocate it with the journal form that uses it.

#### Finding 3

- **Severity:** Low
- **Affected file(s):**
  - `src/lib/server/email/index.ts`
- **Issue description:** Some reminder email helpers use `process.env.RESEND_FROM_ADDRESS || ''` while the rest of the file already relies on validated config from `getEnv()`.
- **Why it matters:** This bypasses the project’s central environment contract and allows an empty sender address fallback in the exact code path that should be strict.
- **Recommended fix:** Use `env.RESEND_FROM_ADDRESS` consistently in all email helpers.

## Priority Fix Plan

1. **Fix notification reliability first**
   - Normalize all email send helpers to a strict failure contract.
   - Prevent `email_notifications` rows from being written unless the email send actually succeeds.
2. **Correct visits action error semantics**
   - Refactor `src/routes/(app)/visits/[id]/+page.server.ts` to preserve `400/404` and redirects.
3. **Shrink the largest route modules**
   - Extract dashboard query/mapping logic and task-page action logic into dedicated server modules.
4. **Expand edit-route abstractions**
   - Move repeated owned-entity update/delete flows into shared helpers or service functions.
5. **Clean low-risk structural debt**
   - Convert API endpoints to `./$types`, remove redundant `params.id as string` casts, remove dead wrapper exports, and standardize `env.RESEND_FROM_ADDRESS`.
