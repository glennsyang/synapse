## Findings

### [P1] Cron endpoint auth bypass when secret is missing

- **Status:** ✅ Remediated (2026-02-25)

- **Affected files/functions:** `src/routes/api/cron/email-notifications/+server.ts` (`POST`)
- **Vulnerability type:** Authentication bypass / fail-open secret handling
- **Risk/exploit scenario:** If `CRON_SECRET` is undefined in runtime, `Authorization: Bearer undefined` satisfies the current equality check and can trigger cron processing by unauthorized callers.
- **Evidence:**
  - `expectedToken` sourced from `process.env.CRON_SECRET`
  - direct comparison to `Bearer ${expectedToken}` without prior non-empty secret guard
- **Recommended fix:**
  1. Fail closed when `CRON_SECRET` is missing (startup validation and request-time guard).
  2. Reject empty/undefined secrets before authorization comparison.
  3. Optional defense-in-depth: scheduler source allowlist and constant-time token comparison.
- **Verification steps:**
  1. Run with `CRON_SECRET` unset.
  2. Send POST with `Authorization: Bearer undefined`.
  3. Confirm endpoint rejects request after fix (401/500) and job is not executed.

**Remediation evidence:**

- `src/routes/api/cron/email-notifications/+server.ts` now rejects execution when `CRON_SECRET` is missing/empty before bearer comparison.

### [P2] Overly permissive CSP policy weakens XSS containment

- **Status:** 🟡 Partially Remediated (2026-02-25)

- **Affected files/functions:** `src/hooks.server.ts` (global response header setup)
- **Vulnerability type:** Browser-side mitigation weakness (CSP hardening)
- **Risk/exploit scenario:** If any injection primitive exists elsewhere, permissive CSP directives make script execution materially easier, increasing exploitability and blast radius.
- **Evidence:**
  - CSP includes `script-src 'self' 'unsafe-inline' 'unsafe-eval'`
  - CSP includes `style-src 'self' 'unsafe-inline'`
- **Recommended fix:**
  1. Move to nonce/hash-based policy for script/style.
  2. Remove `unsafe-eval` unless strictly required.
  3. Tighten baseline directives (`object-src 'none'`, `base-uri 'self'`, `form-action 'self'`).
- **Verification steps:**
  1. Inspect response headers after change.
  2. Confirm no blanket `unsafe-eval` and minimized/removed `unsafe-inline`.
  3. Validate runtime behavior for scripts/styles with nonce/hash policy.

**Remediation evidence:**

- `src/hooks.server.ts` CSP now includes tighter baseline directives: `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, and `frame-src 'none'`.
- Required exceptions are intentionally preserved for compatibility:
  - `script-src 'unsafe-eval'` for layerchart/d3
  - `style-src 'unsafe-inline'` for SvelteKit and Google Fonts usage

### [P2] Sensitive auth/error metadata may leak via logs

- **Status:** ✅ Remediated (2026-02-25)

- **Affected files/functions:**
  - `src/lib/server/auth.ts` (auth event logging)
  - `src/hooks.server.ts` (global error logging)
  - `src/lib/utils/logger.ts` (logger behavior)
- **Vulnerability type:** Information disclosure (log hygiene)
- **Risk/exploit scenario:** Email, forwarded IP values, stack traces, or serialized causes may be exposed in log infrastructure and reused by attackers or during log-store compromise.
- **Evidence:**
  - Sign-in path logs user identifiers and client-provided IP context.
  - Global error handler logs stack/cause details.
- **Recommended fix:**
  1. Redact or hash user identifiers in routine info logs.
  2. Suppress raw stack/cause in production logs (or sanitize aggressively).
  3. Treat forwarded IP headers as untrusted unless known proxy boundary is enforced.
- **Verification steps:**
  1. Trigger sign-in and controlled server error in production-mode logging.
  2. Confirm logs contain no raw PII or full stack/cause payloads.

**Remediation evidence:**

- `src/lib/server/auth.ts` no longer logs email addresses or forwarded IP values in sign-in/verification/password-reset debug paths.
- `src/hooks.server.ts` now passes error objects through sanitized logger usage.
- `src/lib/utils/logger.ts` now suppresses stack traces outside development mode.

### [P3] Password change flow does not revoke other active sessions

- **Status:** ✅ Remediated (2026-02-25)

- **Affected files/functions:** `src/routes/(app)/profile/+page.server.ts` (`changePassword` action)
- **Vulnerability type:** Session lifecycle hardening gap
- **Risk/exploit scenario:** Existing compromised sessions may remain valid after password change, enabling persistence.
- **Evidence:** Previously used `revokeOtherSessions: false`.
- **Recommended fix:** Set secure default to revoke other sessions on password change, or present explicit user choice defaulting to revoke.
- **Verification steps:**
  1. Authenticate on two clients.
  2. Change password on one client.
  3. Confirm second client session is invalidated after fix.

### [P3] Server-side debug console logging present

- **Status:** ✅ Remediated (2026-02-25)

- **Affected files/functions:** `src/routes/(app)/meditation/routines/[id]/+page.server.ts` (`load` error path)
- **Vulnerability type:** Information leakage hardening
- **Risk/exploit scenario:** Raw error serialization can leak internal details and violate logging policy.
- **Evidence:** Previously had `console.log` in server error handling path.
- **Recommended fix:** Remove `console.log`; use structured logger with sanitization/redaction policy.
- **Verification steps:** Trigger error path and confirm only sanitized logger output appears.
